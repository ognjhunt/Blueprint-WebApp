# Job-first automation website

Owner authorization: October 21, 2026, “please implement your recommendations into our website in FULL,” with a simple, understandable UI. The accepted recommendations are job-first positioning, separate deployment/technology partner paths, comparable delivery proposals, customer selection, explicit pilot agreement and recorded outcomes. The owner subsequently clarified that video remains required, descriptions can come from the existing video analysis, and the existing example/how-it-works page should be preserved and modified.

## Scope

- Public pages explain video → analysis and drafted brief → site simulation → robot/policy comparison → delivery proposals → direct pilot → measured outcome. Preserve the original example/how-it-works experience and update its explanation.
- Existing approved robot illustrations, reduced-motion handling and privacy controls remain.
- Buyer intake starts with video upload or the existing recording path. A manual job description is optional; reuse the existing video analysis to draft it. Frequency and buying plans remain optional. No budget is required for free assessment.
- Saving an account, capture session or upload draft before footage arrives is capture setup, not completed intake for assessment. Actual assessment, simulation and evaluation require the real video and its existing provenance/rights bindings. Do not replace them with a text-only path or a new analysis service.
- Reviewed partner applications distinguish installation/support from technology access.
- The owner workspace records requirements, options, versioned proposals, selection, pilot agreement and customer-reported outcomes in Blueprint's existing datastore.
- Admin tools populate proposals and record agreement references; an API alone is not the operating interface.
- Selection is not contract award. The customer and delivery partner agree physical work directly.
- Customer observations remain separate from Pipeline-owned scientific verdicts and Physical Outcome Joins.

## Commercial and evidence boundaries

The existing beta remains free. This implementation adds no assessment fee, success fee, checkout, provider spend or automatic contract award. No provider, passed evaluation, completed deployment or support coverage is invented. Proposed prices describe a delivery partner's physical work, not a charge by Blueprint.

Existing site recording, training, anonymized-card and account permissions remain binding. Historical records, previous legal versions, API identifiers and scientific evaluation artifacts retain their contracts.

## Job evidence integration — October 21

The existing admin job detail's delivery workflow now has an evidence section. An operator can record an options review without creating any run; when a technical question matters, the same panel saves it to Pipeline, shows its next action and limitations, refreshes it, runs a Pipeline-selected permitted local method, or cancels that request. This action grants no paid resources. Description-only jobs retain no fabricated capture, testbed or run. A missing scoped scientific request produces an information request; an unavailable service leaves the saved question retryable under the same identity.

The managed policy setup in this panel uses the existing configured-scene offering and run preparation flow. It lists only an actual scene bound to this job's current task context and preserves existing admission and resource authority. Blueprint can operate the supported managed policy pair without inviting a technology team to run it. The existing approved team integration remains available. Controls-pending scenes remain diagnostics.

Pipeline owns the plan, exact native Decision Envelope, abstention and claim ceilings. The signed `/api/internal/job-evidence-publications` receiver stores publications immutably below the job, validates the saved request/brief/task/testbed binding, and returns a replay-safe receipt. Original Python canonical JSON bytes accompany native artifacts so JavaScript does not recalculate their scientific identities using different float or key-order rules. The imported canonical handoff is `contracts/pipeline/decision-evidence-router.v1/`; the older similarly named JSON file remains an explicit legacy reader, not the native producer contract.

The owner workspace shows factual results, limitations, next actions and exact references. It receives neither raw scientific documents, service credentials nor authorization candidates. Proposals can optionally reference an exact job result or a managed run result; summary-only historical proposals remain readable. The owner can open a readable, authorized copy of a referenced immutable local result. Buying budgets can stale a quote without invalidating unchanged evidence. Technical brief or source/configuration changes end the affected result's current applicability. A result never selects a proposal, creates an agreement or turns a customer-reported outcome into physical proof.

`JOB_EVIDENCE_PIPELINE_URL` may specify the existing Pipeline service endpoint; otherwise its URL is derived from the existing request/plan forwarding URL. Existing server service credentials and configured client identity sign requests. Pipeline publishes back to the existing website origin using its sync secret. No new credential service, worker flag, outreach send or payment path is introduced. Deployment of these commits and configuration/readback on the existing release path are separate from local verification.

Description-only brief confirmation no longer marks absent video for processing or leads the owner into the legacy filming status. Once a pilot agreement exists, a brief edit cannot silently change its agreed physical scope. The existing outcome-recording permission still has to be present in the agreement; later permission amendments remain outside this change.
